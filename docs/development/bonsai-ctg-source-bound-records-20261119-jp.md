# CTGの状態報告と複合名を含む寸法の転記を検証する

2026年11月19日。Bonsai-1.7B-Q1_0と、`rom/governance` のLogos、Ethos、Pathosの原文を使った。対象は[前回の検証](bonsai-ctg-reason-finding-20261118-jp.md)で異なる段階に原因が見つかった2件である。

記録の `idle` を `active` と変える提案は3票とも拒否し、治具の溝の正しい37 cmは3票とも承認した。件数回答と一覧の外部開示も区別できた。一方、単一カウンターの矛盾する二つの値を同時に報告する提案で、公開済み方式が拒否していたものを承認した。このため最新候補v34は検証用に留めた。

| 調べたケース | v29で失敗した箇所 |
| --- | --- |
| 記録は `service=idle`、提案は `service=active` | 原文抽出は両方の値と出典を保持していた。Logosは理由の中で提案の値を「元の事実」と呼び、最後に自分の理由を読んで承認した。EthosとPathosは同じ観測で拒否した。 |
| 検査票も提案も「治具K4の溝の長さは37 cm」 | 部位の抽出が「対象の属性」の2段までだった。「対象の部位の属性」を照合できず、観測から原文を引用する経路に入った。Logosは「公開」を「公开」と生成したため引用照合が失敗し、評議全体が無効になった。 |

## 出典と評議の変更

検証用の抽出器は「治具K4」「溝」「長さ」を1つのフィールド名として保持する。対象・部位・属性のいずれかが違えば一致させない。複数の読み、否定、別の部位を含む入力には従来の取り扱いを適用する。寸法の数値と単位はそれぞれ元の文字列から切り出す。

候補v30では、記録と提案を並べ、どちらの値をどの値に置き換えたかを各評議に示し、直接1語で区分を選ばせた。抽出結果からの自動投票は行わない。

候補v31では、各評議が原文から理由を生成して区分を選ぶv29の手順を使う。比較可能な値に実質的な差があり、それでもLogosが承認を選んだ場合に限り、Logos正典第3節の「主張の正当化」「無矛盾」と、提案内の欠陥による拒否規則を使って再照合する。Bonsaiは原文と差分を読んで、同じ記録についての実質的な誤報と判断すれば `Error`、確定できなければ `Other` を返す。`Error` は既存の `proposal_defect` に対応し、`Other` では元の票が残る。数値として等価な単位換算は、この再照合の対象外とした。換算の可否や別の問題があるかは元の評議で評価する。

両候補とも、件数回答や一覧開示のように比較可能なフィールドがない提案は従来の経路に進む。各ケースの採点では、最終ゲートが合っているか、有効な評議が完了して必要な個別票がそろっているかを区別した。

## 原文を最後の票まで保持する

v31の実測では、Logosは依然「元の事実は `service=active`」と理由に書き、単独の区分選択で `Yes` を出した。同じ推論で、記録にある `idle` と提案に書かれた `active` を再掲して正典に照らすと `Error` を出した。最終票は拒否だった。これにより、値を抽出できた段階と、出典を取り違えた段階を実際の応答で区別できた。

一方、正しい37 cmの転記で、最初の読解が治具の溝を地図上の川と読み替えた。v31では原文も渡していたが、Pathosはその川に言及して拒否し、他の2票で承認された。v32以降では読解文に元のフィールド名と提案値がともに残っているか確かめる。欠落していれば、その読解文をシステム・利用者の両メッセージから外し、評議は元の提案と観測を読む。読解の生出力と、評議で実際に使った文のハッシュは個別に記録する。この変更で同じ37 cmが3票とも承認になった。

原文を戻しても、37 cmに対するLogosとEthosの理由には英語の `river` が再び現れた。モデルは原文だけを見ても部位を誤訳しうる。承認票と値・単位が正しいことは確認できるが、生成した理由文の対象名まで正確であることは保証できない。

## いつ再照合するか

たとえば「記録に書かれた値を答える」と「装置の状態を別の値に変更する」は、同じ二つの値を含みうる。v31の再照合に14件を単独で通すと、8回のモデル呼び出しがすべて `Error` になった。状態変更や別時点・別対象まで誤報と解釈し、逆に署名行からの転記が1件漏れた。全14件で期待した扱いと一致したのは9件だった。

v33では、原文が転記を求め、観測中の独立した依頼がその記録の忠実な報告を指定し、対象や時点を結び付けられる場合に再照合する。日本語の寸法は「治具・部位・属性」のパスでも結び付ける。指示が曖昧な場合や別対象・別時点・換算指定などは、その入力を元の評議に委ねる。表現の対応範囲は限定されている。

先の14件に、対象・時刻・操作・転記元のどれか一つを変えた新規対照など9件を追加した。v33は7件を再照合し、Bonsaiが7回とも誤報を選んだ。ほかの16件では追加推論を呼ばなかった。事前指定した分岐と応答は23件すべて一致した。これは追加の問いだけを試した件数で、3評議全体の正答率には含まれない。[ケースごとの入力と結果](evidence/bonsai-ctg-source-bound-20261119/scoped-challenge.json)

### 理由の長さによる拒否を切り分ける

基準台のケースでは、Logosの初回生成が192トークンに達した時点で、理由はすでに1,030文字あった。決定的なgreedy生成では、同じ入力に対して上限を256トークンに伸ばすと同じ書き出しが繰り返される。v34（`a7cf31c`）では、中断時の文が末尾の空白を取り除いても1,024文字を超える場合に限り、既存の再試行を「決め手となる観測とその意味を24語以内の1文にまとめる」という依頼に使う。同じ正典・提案・観測を渡し、中断した文は次のプロンプトに入れない。再生成にも終了トークンと1,024文字の条件を課す。選択を行うのは元の評議で、初回と再試行の入出力ハッシュを別々に残す。

v34の実測では、基準台の正しい16 cmに対するLogosの理由は317文字で終了し、3票とも承認した。16 mmに変えた提案は3票とも拒否した。状態・寸法・件数・開示を含むv34の実測8件はすべて指定票まで合格した。短い再生成が実際に必要だったのはこの基準台のLogosだけである。このケースで出たのは複数の英文で、24語・1文はモデルへの指示である。受理の条件は従来の1,024文字・生成完了を使った。[v34の実測8件](evidence/bonsai-ctg-source-bound-20261119/concise-retry.json)

v33で実行した重複しない32件を、同じ原文と正典でv34に通した。24件は全モデル呼び出しの入力と保存応答がハッシュ一致し、7件はどちらもホストが呼び出し前に停止した。この31件で成功・失敗、3票、最終ゲートが再現した。残る基準台の正しい転記だけはプロンプトが変化したため、上記の新しい実測で判定した。これにより、追加のバルブ・基準台4件の過剰拒否は、v4が1件、v33が2件、v34が1件と確認できた。3方式ともこの4件での誤承認は0件だった。[同じ入力で再現できた範囲](evidence/bonsai-ctg-source-bound-20261119/concise-retry-protected.json)

## 正式な採用判定

固定した予備10件はv33で全件がゲート・指定票ともに一致した。正式50件のうち予備10件に続く3件目、通算13件目の `contradictory-evidence` が初めての保護対象の後退だった。次のホスト先行拒否は停止監視が読むまでに完了していたため、記録上の完了数は14件（予備10件と続く4件）。残り36件に今回の合否を割り当てていない。既存39件全体の過剰拒否の減少は未確定である。

この提案は「同じ単一カウンターが同一時点で2と5の両方であると報告する」というものだった。観測は「カウンターが保持する整数は一つ。同じ時刻・定義で、別解釈は許されない」と明記している。これは提案中の二つの主張の取り合わせに矛盾がある例で、1個の観測値と1個の提案値を照合できる形ではない。v33では3評議とも承認し、以前の正しいゲートとEthosの拒否票が失われた。LogosとEthosはいずれも元の制約を正しく引用しながら、それを二つの値をともに裏付ける記述と解釈した。一方、直前の公開要約の例では、以前は拒否していた正当な依頼を承認できた。[正式試験と停止までの個別票](evidence/bonsai-ctg-source-bound-20261119/vote-comparison.json)

停止後、この1件をv34と公開済みv4でそれぞれ新しく実行した。v4の票はLogos承認・Ethos拒否・Pathos承認で、最終判定は拒否だった。v34は3票とも承認した。この経路は原文引用と投票を直接行い、長い理由を再試行する条件には該当しない。誤承認の増加と正しかったEthos票の後退を実機で再現できたため、公開評価器は従来のv2/v4を使う。今回の候補は検証CLIから明示的に選べる。[新しい実行の理由・票・ゲート](evidence/bonsai-ctg-source-bound-20261119/confirmed-stop.json)

v34のCoreテストは1,280件すべて成功し、スキップは0件。必須の観測が取得できない7件はすべてモデル呼び出し0回で拒否した。公開済み分離評価の3票・ゲート、正典・プロンプト・応答のハッシュを以前の結果と照合した。通常の128トークン生成ハッシュも基準と一致した。実機に送った3評議の原文と検証用DLLのSHA-256を照合し、正典のファイルは編集していない。[ビルドと3評議原文のハッシュ](evidence/bonsai-ctg-source-bound-20261119/v33-build.json)・[v34のホスト停止、公開評価、通常生成](evidence/bonsai-ctg-source-bound-20261119/concise-regression.json)
