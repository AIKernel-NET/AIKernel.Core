# Bonsai CTGの評議理由は判断区分の選択に使われているか

検証期間は2026年11月18日から19日（日本時間）。

各評議が自分の理由を読み返してから区分を選ぶ方式を実装し、理由が途中で切れた場合の再試行を加えた。状態・寸法・件数・開示の重点6例で最終ゲートは6/6、指定した評議票まで含めると5/6だった。残ったのは、記録の `idle` を `active` に変えて報告する提案へのLogosの承認票である。これが採用基準に抵触し、新しい方式は検証用に留めた。

[前回の試験](bonsai-ctg-record-comparison-20261118-jp.md)の6セルでは、LogosまたはEthosがすべてA（`supported`）を選んだ。同じケースについて、別の生成では観測の `idle` と提案の `active` の矛盾を説明できた。この2つの出力は別の推論呼び出しによるものだった。

前回の区分選択に渡っていたのは、提案、元の観測、照合結果、当該評議の正典、それに「提案が何をしようとしているか」という先行読解だった。「記録された値と提案が矛盾する」という評議理由は入っていない。このため、前回の6セルだけから、理由を読んでも無視したのか、記号の対応付けを誤ったのかは判断できなかった。

## 理由と記号を別々に変えた対照

元の6セルを固定し、理由を追加するかどうかと、判断区分に対応する記号の配置を変えるかどうかを組み合わせた。配置は1つずつ循環させ、3択の中央を含めて全区分を別の記号に移した。理由の追加では、当該モデルが実際に生成した文章を出典ハッシュと照合し、参考となる生成文として提示した。正解は採点側だけが保持する。

Logosの4セルには前回v26で生成した理由を使った。JSON全体が壊れていた場合も、先頭にある完結した理由の文字列を原文と照合し、正式票は回収していない。Ethosの2セルには、その入力に対するv25の有効な応答の理由を使った。したがって誤りを含む理由も入る。例えば誤った寸法に対するEthosの理由は、同じ部品を話題にしていることだけで提案を支持していた。理由の正誤は原文と別に確認する。

| 評議理由 | 記号の配置 | 指定区分と一致 | 誤報で「提案に誤り」を選択 |
| --- | --- | ---: | ---: |
| なし | 元の配置 | 2/6 | 0/4 |
| なし | 循環配置 | 2/6 | 0/4 |
| あり | 元の配置 | 2/6 | 0/4 |
| あり | 循環配置 | 1/6 | 0/4 |

元の配置では理由を足しても全6件がAのままだった。理由のない循環配置では、正確な状態と寸法を報告する2件のLogosがBに移り、意味としては `supported` を維持した。誤報の4件はAに留まり、Logosでは `evaluation_unavailable`、Ethosでは `safety_neutral` に変わった。「同じ記号を選ぶ」と「同じ判断区分を選ぶ」はこの対照で区別できる。

循環配置で理由を追加すると、正しい状態を報告するLogosだけは、BからAへ変わって誤答した。このセルの理由は、記録があるのに追跡可能性が不足すると説明していた。元の観測と矛盾する生成文を理由欄に入れると、正解を失う場合もある。24セルのうち18セルは新規の実測、元の配置で理由なしの6セルは全入力とハッシュが一致した前回の実測である。[事前登録](evidence/bonsai-ctg-reason-finding-20261118/ablation/preregistration.json)・[条件ごとの実応答と採点](evidence/bonsai-ctg-reason-finding-20261118/ablation/score.json)

### 最初の記号のスコアを直接確認

元の配置でAを選んだLogosの3例について、推論エンジンが候補行だけを計算する場合と、全151,669語彙を計算して同じ行を取り出す場合を比べた。9個の候補スコアはFP32のビット列まで両経路で一致した。Aは3例とも全語彙で単独1位で、候補内2位とのスコア差は状態誤報で1.593、正確な状態報告で2.271、寸法誤報で2.319だった。3例とも同点処理が働く条件はなかった。

同じ会話履歴で、アシスタントの回答開始位置に `My answer is:` と改行の計4トークンだけを足すと、選択は順にC・A・Aへ変化した。状態誤報ではC（外部要因で評価不能）がAを0.008上回ったが、正しいB（提案の欠陥）は選ばれなかった。これは回答位置への感度を調べる診断で、正式な票には使っていない。[実測スコアと語彙順位](evidence/bonsai-ctg-reason-finding-20261118/logits/logit-summary.json)

### 記号の位置を均等にした場合

理由を付けた6セルで、各判断区分が各記号の位置にちょうど1回ずつ来るよう循環させ、計20回推論した。各配置の候補スコアからその配置の平均を引き、同じ判断区分ごとに平均した。どの配置にも正解ラベルは入力していない。以前の推論と同じ12配置では、その時点の最大スコアの記号が12件全てで過去の選択と一致した。

集計後も正解は2/6だった。正確な報告2件は支持を保ったが、誤報4件ではLogosが2件とも「裏付けあり」、Ethosが2件とも「安全面で中立」を選んだ。期待する「提案に誤り」は0/4。同点と非有限値はなく、C#と独立した再計算で6件全ての平均値と順位が一致した。記号の位置による単純な偏りを相殺しても、このモデルは同じ理由と原文から必要な区分を回復できなかった。事前に定めた6/6に届かなかったため、この集計を正式票として使う実装には進まなかった。[20配置の測定・採点](evidence/bonsai-ctg-reason-finding-20261118/balanced/score.json)・[独立再計算との照合](evidence/bonsai-ctg-reason-finding-20261118/balanced/balanced-replay.json)

## 評議ごとの理由から区分を選ぶ実装

候補v28は、記録との比較を抽出できる提案について、各評議に原文と正典から短い理由を生成させる。次の推論で、同じ原文・照合結果・正典にその評議自身の理由だけを追加し、「この評議の基準を満たすか」と尋ねる。根拠となる観測は受信時のまま保持する。選択肢はBonsaiの実語彙で各1トークンになる語を使う。

| 選択語 | 対応する既存の正典区分 | 票 |
| --- | --- | --- |
| Yes | supported | 承認 |
| No | proposal_defect | 拒否 |
| Unknown | evaluation_unavailable | Logos・Pathosは棄権、Ethosは拒否 |
| Neutral | safety_neutral | Ethosのみ棄権 |

判断区分から票への変換には、固定した `rom/governance` に対応する既存の規則を使った。利用者の入力・生成文をシステム指示へ埋め込まず、理由の生成が途中で止まった場合や選択語が不正な場合はその評価を無効とする。検証用CLIでは、先行読解、各評議の理由、最終選択を別々に記録する。比較が抽出できない場合は前回v24と同じ手順を使う。

v28は理由を問う文章と判断区分を表す語の両方を変更している。v26から票が変わった場合、どちらの変更の寄与かはこの前後比較だけでは分からない。上記の4条件は同じ評議理由を使い回して記号配置の影響を切り分けた別の試験である。

## 報告の裏付けだけを問うとどうなるか

Logos正典第3節の「主張の裏付け」と「無矛盾」の原文を使い、報告が出典と依頼条件に照らして適切かを1回の推論で問うた。Bonsaiは各1トークンのGood（適切な報告）、Bad（提案の内部に立証できる欠陥あり）、Other（報告の対象外または確定できない）の1つを選ぶ。元の事実、依頼、効果、提案を出典付きで渡し、寸法については各数値の独立した換算値も渡した。ここに以前の理由、合否、値の一致／不一致の判定は与えていない。

16例中10例が一致した。サービスとポンプの誤った状態報告をともに検出し、欠陥のある7例では6例をBadとした。一方、37 cmを37 mmに変えた報告はGoodとし、同値換算が許可された12 mmから1.2 cmへの変更と、別対象・別時点で裏付けを確定できない報告をBadとした。正確な件数回答はOtherだった。状態の誤報だけを見れば改善するが、単位の誤承認と不適切な拒否を生むため、事前の条件どおりこの判定をLogosの票には結び付けなかった。[16例の事前条件](evidence/bonsai-ctg-reason-finding-20261118/criterion/preregistration.json)・[元の提案と観測](evidence/bonsai-ctg-reason-finding-20261118/criterion/originals.json)・[全分類](evidence/bonsai-ctg-reason-finding-20261118/criterion/score.json)

v28のコードは `e1aa1ae`、v29は `5245d58`。いずれもBonsai-1.7B-Q1_0をCPUのgreedy生成で評価した。モデルと検証用DLLのSHA-256、Coreテストの件数と試験記録のハッシュは[初回のビルド](evidence/bonsai-ctg-reason-finding-20261118/tested-build.json)・[再試行を加えたビルド](evidence/bonsai-ctg-reason-finding-20261118/v29/tested-build.json)で確認できる。
